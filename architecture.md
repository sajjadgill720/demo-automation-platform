# Architecture - Convoa Demo Automation Subservice

This document outlines the architectural boundaries, design patterns, and engineering choices for the Convoa Demo Automation Backend Subservice. Any future modifications must align with these decisions.

---

## 1. System Topology & Data Flow

```mermaid
graph TD
    Client[Landing Page/POST Client] -->|1. Submit Request| MainAPI[FastAPI: POST /api/demo-request]
    MainAPI -->|2. Validate & Sanitize| Sanitizer[Sanitization Helper]
    MainAPI -->|3. Compile Persona| PromptEngine[agents.py: compile_lead_prompt]
    MainAPI -->|4. Save Lead status=pending| DB[(PostgreSQL via Supabase)]
    MainAPI -->|5. Enqueue background task| BgTask[FastAPI BackgroundTasks]
    MainAPI -->|6. Return lead_id| Client

    BgTask -->|7. Invoke Task| ProvTask[agents.py: provision_vapi_assistant_task]
    ProvTask -->|8. Call creation with 1x retry| VapiAPI[Vapi REST API: POST /assistant]
    VapiAPI -->|9. Returns assistant_id| ProvTask
    ProvTask -->|10. Update status=active / failed| DB

    Client -->|11. Poll Status| MainAPI[FastAPI: GET /api/demo-request/{lead_id}]
    Client -->|12. End session| EndSessionAPI[FastAPI: POST /api/demo-request/{lead_id}/end-session]
    EndSessionAPI -->|13. Call deletion with 1x retry| VapiDelete[Vapi REST API: DELETE /assistant/{id}]
    EndSessionAPI -->|14. Update status=completed| DB
```

## 2. Database Schema (leads table)

To prevent code redundancy, we use **SQLModel** which integrates with SQLAlchemy for ORM database operations and Pydantic for API validations/schemas. The database is unified under **PostgreSQL (Supabase)**, managed via **Alembic migrations**.

* **id**: `UUID` (Primary Key, autogenerated on insert)
* **company_name**: `VARCHAR(255)` (Required)
* **contact_name**: `VARCHAR(255)` (Required)
* **contact_email**: `VARCHAR(255)` (Required, checked via Email validation)
* **contact_phone**: `VARCHAR(50)` (Required)
* **industry**: `VARCHAR(255)` (Required)
* **rendered_prompt**: `TEXT` (Required, full persona markdown output saved for auditing)
* **assistant_id**: `VARCHAR(255)` (Nullable, stores Vapi assistant ID)
* **agent_status**: `ENUM ('pending', 'active', 'completed', 'failed')` (Defaults to `pending`)
* **failure_reason**: `TEXT` (Nullable, holds error details on persistent Vapi creation failures)
* **created_at**: `TIMESTAMP` (Defaults to UTC now)
* **updated_at**: `TIMESTAMP` (Defaults to UTC now, updated on change)

---

## 3. Background Task Execution Model
* **Current MVP Approach**: Uses FastAPI `BackgroundTasks` to keep the API responsive while making downstream HTTP calls to Vapi.
* **Warning / Constraints**: FastAPI `BackgroundTasks` are stored in memory; they do not survive application restarts and do not support advanced task queues.
* **Production Path**: If the system transitions out of MVP, this execution layer must be replaced with **Celery + Redis** (or a similar message broker setup) for durability.

---

## 4. API Resilience & Retry Policies
Downstream calls to the Vapi API must follow a transient-only retry policy:
1. **Transient Failures (Retry 1x)**: Catch network timeouts, connection issues, or HTTP 5xx codes. Pause for a backoff (e.g. 1 second) and retry exactly once.
2. **Persistent Failures (No Retry)**: Do not retry HTTP 4xx codes (e.g. 401 Unauthorized, 400 Bad Request, 422 Unprocessable). These errors fail immediately.
3. **Graceful Failures**: If retries are exhausted or a persistent failure is met, the background task writes the status to `failed` and records the error payload in the `failure_reason` field. It **must not** raise an unhandled exception or crash the FastAPI server thread.

---

## 5. Security & Sanitization Policy
Because user inputs are dynamically interpolated into a system prompt template, the system must perform defensive sanitization to prevent prompt injection attacks:
* **Max Length**: Fields are sliced to a maximum of 100 characters.
* **Char Blocking**: Strip characters commonly used to structure LLM instructions, specifically braces `{}`, brackets `[]`, and angle brackets `<>`.
* **Keyword Filtering**: Case-insensitive filtering strips instructions-override terms (e.g. "ignore previous instructions", "system prompt", "you are now", "system:").

---

## 6. Structured Logging Standards
The subservice uses python's standard logging library formatted into single-line JSON statements. Log records include:
* Standard fields: `timestamp`, `level`, `message`, `logger`, `module`, `funcName`, `lineNo`.
* Contextual extra fields: `lead_id`, `assistant_id`, `status_code` when processing operations.
* Third-party log levels (e.g., `uvicorn.access`, `sqlalchemy.engine`) are suppressed to `WARNING` to prevent log noise.

---

## 7. Known Gaps / Future Enhancements
* **Orphaned Assistant Cleanup**: Clients abandoning the landing page without ending the demo session leave Vapi assistants active. 
* **Fix**: Implement a cron cleanup worker (e.g. daily) that queries `leads` matching `agent_status = "active"` where `created_at` is older than N hours, calls Vapi delete, and marks status as completed.
